# O01 — Operation Model

Date: 2026-10-07

## Goal

O01 gives GCTG a small, explicit operation lifecycle.

An operation is a unit of work that can be observed without exposing implementation details.

## States

The model supports:

- queued
- running
- succeeded
- failed
- cancelled
- recovered

Each operation has:

- stable operation ID;
- name;
- start time;
- optional finish time;
- optional parent operation;
- metadata;
- optional failure message.

## Runtime integration

ApplicationRuntime owns one OperationService.

Repository indexing creates an operation:

1. queued;
2. running;
3. succeeded or failed.

The existing index return value is unchanged, so current callers remain compatible.

## Surfaces

Operations are available through:

- HTTP: /api/operations
- MCP: operations

The optional id parameter returns one operation; without it, the current runtime operation list is returned.

## Scope boundary

O01 is intentionally in-memory.

Persistent bounded operation history belongs to O04.

Progress stages belong to O02.

Health aggregation belongs to O03.

## Tests

Tests cover:

- successful lifecycle;
- failed lifecycle;
- parent operation linkage;
- deterministic listing.

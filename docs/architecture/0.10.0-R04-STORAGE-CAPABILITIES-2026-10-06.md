# 0.10.0 R04 — Storage Capability Boundaries

Date: 2026-10-06
Baseline: R03

## Objective

Separate storage responsibilities at the application boundary without forcing a storage-engine rewrite.

## Graph storage

The existing `GraphStore` contract remains available for compatibility.

New capability contracts split its responsibilities into:

- `GraphSnapshotStore`;
- `GraphNodeStore`;
- `GraphQueryReader`;
- `GraphReadStore`;
- `GraphWriteStore`;
- `GraphStorage`.

The JSON graph adapter implements the capability composition while remaining compatible with existing consumers.

## Semantic cache

The cache now exposes:

- `SemanticCacheReader`;
- `SemanticCacheWriter`;
- `SemanticCache`;
- `SemanticStorage`.

The JSON cache remains the current adapter.

## Why this is R04

The goal is not to replace JSON storage yet. The goal is to stop application services from depending on a monolithic persistence capability.

This makes future storage implementations possible without changing the application layer.

## Compatibility

No public GraphStore behavior was removed.

Existing snapshot, node lookup and query operations continue to use the same JSON implementation.

## Verification

- Storage capability contract tests added.
- Existing GraphStore contract retained.
- R03 surface-conformance architecture remains intact.

## Follow-up

R05 should use these capability boundaries in the application runtime and begin removing direct infrastructure-type dependencies from higher-level composition.

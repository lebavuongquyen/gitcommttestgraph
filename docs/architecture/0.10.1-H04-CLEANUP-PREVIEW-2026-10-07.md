# H04 — Cleanup Preview and Apply

Date: 2026-10-07

## Goal

H04 turns a retention result into a safe maintenance workflow.

The core rule is:

**preview first, then apply exactly that preview.**

No cleanup operation is allowed to invent a new deletion set during apply.

## Preview

SnapshotCleanupService.preview():

1. receives exact commit IDs;
2. reads current snapshot metadata;
3. resolves exact physical snapshot records;
4. sorts them deterministically;
5. creates a proof ID from the exact records.

The preview contains the physical path, commit, analyzer version, configuration fingerprint and current size.

## Apply

SnapshotCleanupService.apply():

1. verifies the preview proof;
2. reloads current storage metadata;
3. treats already-missing items as idempotent;
4. rejects changed items as stale;
5. deletes only the exact preview records;
6. updates the manifest under the storage lock.

The physical delete is GCTG-owned storage only. Git history is never changed.

## Interruption safety

Each snapshot deletion is followed by a manifest update.

If a process stops between items, a later apply can reuse the same preview:

- already removed items are reported as alreadyMissing;
- remaining exact items continue;
- changed items fail closed as stale.

## Surfaces

H04 is exposed through:

- HTTP: POST /api/cleanup/preview
- HTTP: POST /api/cleanup/apply
- MCP: cleanup_preview
- MCP: cleanup_apply

## Scope boundary

H04 does not decide whether a snapshot should be retained. H03 provides the retention decision.

H04 also does not mutate Git, branches, tags or commits.

## Tests

Tests verify:

- deterministic preview identity;
- stale preview rejection;
- idempotent repeated apply.

## Definition of Done

- [x] preview is deterministic;
- [x] apply requires exact preview proof;
- [x] stale records fail closed;
- [x] repeated apply is idempotent;
- [x] physical storage deletion is isolated from Git;
- [x] storage locking is reused;
- [x] HTTP and MCP surfaces exist;
- [x] tests and documentation exist.

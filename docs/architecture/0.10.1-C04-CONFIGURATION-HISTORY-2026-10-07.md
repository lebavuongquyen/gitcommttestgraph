# C04 — Configuration History and Reload

Date: 2026-10-07

## Goal

C04 makes configuration changes traceable and makes reload behavior explicit.

A fresher-friendly mental model is:

1. .gctg/config.json is the current repository configuration.
2. Each successful update adds one line to .gctg/config-history.jsonl.
3. Each history line contains an operation ID, timestamp, and validated configuration.
4. The runtime keeps one configuration snapshot while an operation is running.
5. A later explicit reload replaces the runtime snapshot with the current repository configuration.

## Why this exists

Without history, a changed setting is difficult to explain later. Without an explicit reload action, callers cannot clearly tell when an already-created runtime should start using a changed repository configuration.

C04 keeps the behavior deterministic and simple.

## Storage

config-history.jsonl is append-only from the application point of view.

It is intentionally separate from config.json:

- config.json = current state
- config-history.jsonl = change evidence

The history store does not rewrite Git history and does not attempt to infer who made a change.

## Runtime behavior

ApplicationRuntime exposes:

- updateConfiguration() — persist and immediately update the runtime snapshot.
- reloadConfiguration() — explicitly re-read repository configuration.
- configurationHistory() — read the recorded change history.

An operation already using the runtime continues to use the configuration snapshot captured for that runtime operation. A reload affects subsequent operations.

## MCP

The existing configuration tool now supports:

- get
- update
- history
- reload

No second configuration business layer is introduced.

## Scope boundary

C04 does not attempt to provide:

- user identity or authentication;
- distributed configuration synchronization;
- Git history mutation;
- secret storage;
- automatic background reloads;
- unlimited history management.

Those concerns belong to later lifecycle/operations work if evidence requires them.

## Tests

The C04 unit tests verify:

- every successful update creates an operation record;
- timestamps are valid;
- history preserves update order;
- history survives separate store instances;
- the latest configuration is recorded correctly.

## Definition of Done

- [x] append-only configuration evidence exists;
- [x] operation ID and timestamp are recorded;
- [x] explicit runtime reload exists;
- [x] configuration history is exposed through the application runtime;
- [x] MCP exposes history and reload;
- [x] tests cover persistence and ordering;
- [x] documentation is complete.

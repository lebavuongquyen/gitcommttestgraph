# 0.10.2 O05 — Failure Taxonomy

Date: 2026-10-07
Status: IMPLEMENTED

## Goal

O05 gives failed operations a deterministic failure category so health, operation history and later recovery can reason about failures without parsing free-form messages.

## Categories

- validation
- git
- analysis
- storage
- corruption
- resource
- execution
- external_provider
- recovery

Typed GCTG errors are mapped by stable error code.

Unknown errors use deterministic message-based fallback classification and remain safe for persistence through the existing redaction policy.

## Operation integration

Failed OperationRecord entries now carry failureCategory.

The original error message remains available in its redacted form.

Successful, cancelled and recovered operations do not require a failure category.

## Retry signal

Failure classification also exposes a conservative retryable flag.

Retryable categories are git, resource and external_provider.

This flag is advisory only. O05 does not automatically retry operations.

## Scope boundary

O05 does not introduce a recovery engine, retry scheduler or provider-specific recovery policy.

Those remain later recovery/operations work.

## Tests

Coverage includes deterministic classification for typed errors, generic fallback behavior and propagation of failureCategory into OperationRecord.

## Definition of Done

- [x] stable failure categories exist;
- [x] typed errors map deterministically;
- [x] unknown errors have a deterministic fallback;
- [x] operation records retain failure category;
- [x] persisted records validate the category;
- [x] retryability is explicit and conservative;
- [x] tests and documentation exist.

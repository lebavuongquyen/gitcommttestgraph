# 0.10.1 C01 — Configuration Migration Framework

Date: 2026-10-06

## Goal

Make configuration schema changes safe and predictable without changing the current schema.

C01 adds a small migration framework that can:

1. detect the stored schema version;
2. apply registered migrations in order;
3. reject configurations newer than the supported version;
4. create a deterministic backup before writing a migrated configuration;
5. report whether migration happened.

The current supported schema remains **version 1**.

## Why this exists

Configuration files are persisted under `.gctg/config.json`. Future releases may need to change that structure.

Without a migration boundary, a new release would have to choose between:

- rejecting old repositories;
- silently guessing how old data should be interpreted;
- or scattering compatibility code through the configuration service.

C01 gives future changes one explicit place to live.

## Simple flow

```
.gctg/config.json
        |
        v
read schemaVersion
        |
        +---- current ----> validate and use
        |
        +---- older ------> migration registry
        |                       |
        |                       v
        |                  create backup
        |                       |
        |                       v
        |                  save migrated config
        |
        +---- newer ------> reject
```

## Important safety rule

A migration is never written before the original configuration is backed up.

The current JSON store uses:

```
.gctg/config.json.bak
```

The backup path is deterministic so the behavior is easy to understand and test.

## Developer guide

To add a future migration:

1. Add the new target schema to the configuration model.
2. Create a migration from the previous schema.
3. Register the migration with `ConfigurationService`.
4. Keep the migration deterministic.
5. Add a test for the old input and expected new output.
6. Add a test proving the backup contains the original configuration.
7. Update the configuration documentation and changelog.

A migration must not invent missing business evidence. If old data cannot be converted safely, fail clearly instead.

## Current behavior

Schema 1 is current, so normal repositories do not create a backup during configuration resolution.

A schema newer than the supported version is rejected.

A lower schema is rejected unless a matching migration has been explicitly registered.

## Tests

C01 covers:

- current-schema no-op behavior;
- future-schema rejection;
- deterministic registered migration;
- backup-before-write behavior;
- migrated configuration persistence;
- current-schema resolution without unnecessary backup.

## Scope boundary

C01 intentionally does not add:

- secret management;
- configuration change history;
- configuration diff UI;
- automatic reload policy.

Those belong to later configuration work.

## Definition of Done

- migration contract exists;
- current schema remains compatible;
- migration is deterministic;
- backup occurs before migrated persistence;
- migration evidence is returned to the application layer;
- unit tests pass;
- documentation and changelog are updated;
- no public SDK infrastructure is exposed.

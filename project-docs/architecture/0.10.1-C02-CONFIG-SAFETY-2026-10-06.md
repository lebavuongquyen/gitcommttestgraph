# 0.10.1 C02 — Configuration Safety Boundary

Date: 2026-10-06

## Goal

Keep protected values out of ordinary repository configuration and diagnostic output.

This is a small policy boundary, not a security rewrite.

## How it works

Normal settings are stored in .gctg/config.json.

Protected values have a separate application port:

    interface SecureValueProvider {
      getValue(name: string): Promise<string | undefined>;
    }

The current release defines the boundary but does not implement a cloud provider or credential manager.

## Diagnostic safety

Configuration-like objects can be passed through a recursive redaction function.

Known protected field names are replaced with:

    [REDACTED]

Nested objects and arrays are handled too.

## Important limitation

Name-based detection cannot prove that arbitrary data is safe.

A value stored under an innocent field name may still be private.

Therefore the rule is simple:

Do not put protected values into ordinary configuration.

Redaction is an additional safety layer, not permission to store private material.

## For a Fresher / Junior

Think of the system as three boxes:

1. config.json — normal application settings.
2. secure value provider — protected values when a feature needs them.
3. diagnostics — output that must hide protected values.

## Tests

C02 covers deterministic classification, recursive redaction and rejection of classified data from ordinary configuration.

## Scope

This step does not add encryption, authentication, credential rotation, cloud secret management or environment loading.

Those concerns are separate and should only be added when a concrete product requirement needs them.

## Definition of Done

- protected-value classification exists;
- secure-value provider port exists;
- ordinary configuration can reject classified data;
- diagnostic output can redact classified data;
- nested data is tested;
- limitations are documented clearly;
- no broad security refactor is introduced.

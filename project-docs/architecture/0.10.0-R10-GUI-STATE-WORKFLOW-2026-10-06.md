# 0.10 R10 — GUI State and Workflow Hardening

Date: 2026-10-06
Status: Complete
Baseline: a65e4ef

## Objective

Complete the next part of the R05 GUI architecture foundation without starting a large refactor. The browser controller keeps its existing delivery model, while GUI lifecycle state becomes explicit and testable.

## Changes

- Added `src/gui/state.ts` as the typed GUI state boundary.
- Added explicit load states: idle, loading, ready, empty, error and stale.
- Added explicit execution states: idle, running, completed and failed.
- Added pure state transitions for loading, errors, staleness, execution and node selection.
- Exported a browser-safe state script from the same module.
- Updated `src/gui/client.ts` to initialize from the state model and use state transitions for commit loading, node selection and execution.
- Preserved the existing capability catalog, view-model layer and HTTP contract.
- Removed known mojibake presentation strings from the browser controller by normalizing affected UI separators and status text to UTF-8-safe ASCII equivalents.

## Architecture result

The GUI now has three explicit presentation layers:

1. `app.ts` — HTML/document shell.
2. `client.ts` — browser actions, API orchestration and rendering.
3. `state.ts` + `view-models.ts` — typed presentation state and transport normalization.

No application, domain or infrastructure service is introduced into the GUI.

## Tests

Added `tests/contracts/0.10.0-gui-state.contract.test.mjs`.

The R10 gate verifies:

- deterministic load lifecycle transitions;
- deterministic execution lifecycle transitions;
- node selection state;
- browser-safe state script delivery;
- client consumption of the state transitions.

R10 deliberately does not introduce a large GUI rewrite. Feature-level view modules, richer browser workflow infrastructure or a dedicated frontend build system remain candidates for 0.11 only if the readiness audit proves they are necessary.

## Goal

Recover GCTG-derived graph state only when the repository contains enough deterministic evidence to do so. RCV03 never fabricates semantic evidence and never modifies Git history.

## Recovery model

RCV03 has two evidence-backed actions:

1. Rebuild manifest when consistency checking finds only valid physical snapshot objects that are not referenced by the manifest.
2. Rehydrate HEAD when the current Git HEAD has no usable snapshot. The normal deterministic indexer regenerates it from Git source.

## Fail-closed policy

Automatic repair is blocked when consistency evidence contains:

- invalid manifest data;
- duplicate snapshot identity;
- missing physical snapshot object;
- corrupt physical snapshot object.

These conditions require inspection or a future explicit repair workflow. RCV03 does not delete evidence or silently choose between conflicting objects.

## Preview / apply

Repair is deliberately split:

- plan is read-only and explains evidence, actions and blocking reasons;
- apply executes only a plan considered safe;
- after apply, consistency is checked again;
- unresolved consistency issues fail the operation.

## GUI

The Recovery panel now provides:

- Repair preview
- Apply repair

The existing backup, inspect and restore controls remain unchanged.

## HTTP

POST /api/recovery/repair

Supported repair operations:

- operation=repair_plan
- operation=repair_apply

The response contains a plan with safe, healthyBefore, issues, actions and blockedReasons.

## MCP

Tool: recovery_repair

Operations:

- plan
- apply

The MCP adapter calls the same application service as HTTP and GUI.

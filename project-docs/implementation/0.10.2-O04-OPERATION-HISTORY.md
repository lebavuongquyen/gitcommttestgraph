# 0.10.2 O04 — Persistent Operation History

Date: 2026-10-07
Status: IMPLEMENTED

## Goal

O04 turns the runtime operation model into a bounded, persistent and queryable history.

The feature answers:

> What operations has this GCTG instance recently performed, what was their final state, and when did they finish?

It is deliberately small. It is not a general telemetry or log aggregation system.

## Data model

Each persisted record uses the existing OperationRecord contract:

- operation ID;
- operation name;
- lifecycle state;
- start time;
- optional finish time;
- optional parent operation ID;
- optional sanitized error;
- sanitized metadata.

Supported states:

- queued
- running
- succeeded
- failed
- cancelled
- recovered

## Persistence

The repository-local file is .gctg/operations.json.

Writes use repository-safe path validation, temporary-file creation, atomic rename and bounded retention.

The default history limit is 100 records.

Older records are removed from the persisted history deterministically.

The history is GCTG-owned state and never modifies Git history.

## Security boundary

Operation history is diagnostic state, not a secret store.

Metadata keys containing sensitive names such as token, secret, password, authorization, cookie, API key or credential are omitted.

Nested metadata is sanitized recursively with a bounded depth.

Error messages pass through the existing secret-redaction policy.

## Query model

Application query supports operation name, lifecycle state and result limit.

The limit is capped at 100.

The application runtime restores persisted records during startup, so a newly created runtime can inspect history from previous runs.

## Surfaces

### HTTP

GET /api/operations

Optional query parameters: name, state, limit.

Invalid limits are rejected with HTTP 400.

### MCP

Tool: operations

Arguments: id, name, state, limit.

An id returns one restored operation record. Without id, the tool returns the filtered persisted history.

## Scope boundary

O04 does not:

- collect system-wide logs;
- stream telemetry;
- expose secrets;
- automatically retry operations;
- perform recovery;
- mutate Git history;
- replace progress reporting;
- replace health aggregation.

Those concerns remain separate O02, O03 and later recovery capabilities.
